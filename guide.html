Lyzoo Group — Backend & Deployment Guide

Connecting the prototype to Supabase, deploying on GitHub Pages, and validating COGS accuracy before going live.

This guide turns the working UI prototype into a live application. It gives you the exact database schema, the weighted-average COGS logic implemented inside the database (so every screen reads the same numbers), the connection and authentication setup, file-upload handling, a GitHub Pages deployment path, and a testing checklist to confirm the numbers are correct before you point it at real data.

Golden rule — test on a dev project first

Create two Supabase projects: lyzoo-dev (seeded with a copy of a few real orders) and lyzoo-prod (live data). Validate all COGS math against known figures in dev, and only switch the app's keys to prod once it matches. The free tier allows multiple projects at no cost.

3 · Database schema

Five tables model the whole domain. Open Supabase → SQL Editor → paste and run schema.sql. Relationships: a product has many SKUs; a purchase batch has many purchase lines, each referencing a SKU; sales reference a SKU.

products ──< skus >── purchase_lines >── purchase_batches  ·  skus ──< sales 
-- ============ schema.sql ============
create extension if not exists "pgcrypto";

-- Products (e.g. "USB Flash Drive")
create table products (
  id          uuid primary key default gen_random_uuid(),
  name        text not null,
  created_at  timestamptz default now()
);

-- SKUs: the trackable unit. Weight is required (drives COGS).
create table skus (
  id          uuid primary key default gen_random_uuid(),
  product_id  uuid not null references products(id) on delete cascade,
  sku_code    text not null unique,
  label       text,                       -- optional variant label
  weight_g    numeric(10,2) not null check (weight_g > 0),
  created_at  timestamptz default now()
);

-- Purchase batches (one PO / import shipment)
create table purchase_batches (
  id               uuid primary key default gen_random_uuid(),
  po_number        text not null unique,
  product_id       uuid references products(id),
  supplier         text,
  origin           text not null default 'China',  -- 'China' | 'UK'
  currency         text not null default 'USD',     -- 'USD' | 'GBP'
  conversion_rate  numeric(12,4) not null default 1, -- source -> GBP
  shipping_gbp     numeric(12,2) not null default 0,
  tax_gbp          numeric(12,2) not null default 0,
  purchased_on     date not null default current_date,
  created_at       timestamptz default now()
);

-- Line items within a batch
create table purchase_lines (
  id          uuid primary key default gen_random_uuid(),
  batch_id    uuid not null references purchase_batches(id) on delete cascade,
  sku_id      uuid not null references skus(id),
  quantity    integer not null check (quantity > 0),
  unit_price  numeric(12,4) not null check (unit_price >= 0) -- in batch currency
);

-- Sales: additive. Each row is "units sold in this period".
create table sales (
  id          uuid primary key default gen_random_uuid(),
  sku_id      uuid not null references skus(id),
  quantity    integer not null check (quantity > 0),
  sold_on     date not null default current_date,
  created_at  timestamptz default now()
);

create index on skus(product_id);
create index on purchase_lines(batch_id);
create index on purchase_lines(sku_id);
create index on sales(sku_id);

Why sales are additive: instead of overwriting a running total, each sale is its own row. This matches the app's "+ Sold now" flow and keeps an auditable history you can filter by period.

4 · Weighted-average COGS — in the database

Putting the math in SQL views means the number is computed once and every screen (and any report) reads the identical value. The logic mirrors the prototype exactly:

  1. Landed cost per line = (unit price × conversion rate) + additional-charges-per-unit.
  2. Additional charges = (shipping + tax) pooled and allocated by weight: (shipping+tax) ÷ batch total weight × sku weight.
  3. Weighted-average cost per SKU across all batches = Σ(landed × qty) ÷ Σ(qty).
  4. COGS = units sold × weighted-average cost. On-hand value = remaining × weighted-average cost.
-- ============ views.sql ============

-- Total weight of each batch (Σ qty × sku weight)
create or replace view batch_weight as
select pl.batch_id,
       sum(pl.quantity * s.weight_g) as total_weight_g
from purchase_lines pl
join skus s on s.id = pl.sku_id
group by pl.batch_id;

-- Landed cost (GBP) for every purchase line
create or replace view line_landed_cost as
select pl.id            as line_id,
       pl.batch_id,
       pl.sku_id,
       pl.quantity,
       -- goods, converted to GBP
       (pl.unit_price * b.conversion_rate)                            as unit_gbp,
       -- shipping + tax, allocated purely by weight
       ((b.shipping_gbp + b.tax_gbp)
          * (s.weight_g / nullif(bw.total_weight_g, 0)))              as add_per_unit,
       -- full landed unit cost
       (pl.unit_price * b.conversion_rate)
          + ((b.shipping_gbp + b.tax_gbp)
             * (s.weight_g / nullif(bw.total_weight_g, 0)))           as landed_unit_gbp
from purchase_lines pl
join purchase_batches b on b.id = pl.batch_id
join skus s             on s.id = pl.sku_id
join batch_weight bw    on bw.batch_id = pl.batch_id;

-- Weighted-average cost per SKU (pools all batches)
create or replace view sku_avg_cost as
select sku_id,
       sum(quantity)                             as received,
       sum(landed_unit_gbp * quantity)           as total_cost_gbp,
       sum(landed_unit_gbp * quantity)
         / nullif(sum(quantity), 0)              as avg_cost_gbp
from line_landed_cost
group by sku_id;

-- Units sold per SKU (sum of additive sales rows)
create or replace view sku_sold as
select sku_id, coalesce(sum(quantity), 0) as sold
from sales group by sku_id;

-- The inventory / COGS view the app reads
create or replace view inventory_cogs as
select s.id                              as sku_id,
       s.sku_code,
       s.label,
       p.name                            as product,
       coalesce(ac.received, 0)          as received,
       coalesce(ss.sold, 0)              as sold,
       coalesce(ac.received,0) - coalesce(ss.sold,0)          as remaining,
       coalesce(ac.avg_cost_gbp, 0)                           as avg_cost_gbp,
       (coalesce(ac.received,0)-coalesce(ss.sold,0))
          * coalesce(ac.avg_cost_gbp,0)                       as on_hand_value_gbp,
       coalesce(ss.sold,0) * coalesce(ac.avg_cost_gbp,0)      as cogs_gbp
from skus s
join products p       on p.id = s.product_id
left join sku_avg_cost ac on ac.sku_id = s.id
left join sku_sold ss     on ss.sku_id = s.id;

To read it from the app: supabase.from('inventory_cogs').select('*') returns every SKU with live remaining, average cost, on-hand value, and COGS — no math needed in the browser.

5 · Connecting the app

The app ships with this integration built in. Paste your Project URL and anon public key (Supabase → Settings → API) into supabase-config.js — the app runs in demo mode until both are set, then switches to live reads/writes automatically. The anon key is safe in a public repo as long as Row Level Security is on (Section 6).

  anonKey: 'YOUR-ANON-PUBLIC-KEY'
};
<!-- index.html: load the client from CDN -->

6 · Authentication & security

For a single business login: Supabase → Authentication → add your user (email + password), and disable public sign-ups (Providers → Email → turn off "Enable sign-ups"). Then gate the app:

const { data:{ session } } = await db.auth.getSession();
if (!session) showLogin();          // else render the app

await db.auth.signInWithPassword({ email, password });

// Settings page → update the signed-in user's email / password
await db.auth.updateUser({ email: newEmail });
await db.auth.updateUser({ password: newPassword });

Seed the business login in Supabase → Authentication → Users → Add user, e.g. info@lyzoo.co.uk. The prototype's Settings page (Profile + Change password) maps directly to auth.updateUser; the in-app credential check in the prototype is demo-only — real auth must go through Supabase.

Turn on Row Level Security so the anon key can't read/write without a logged-in session. Run policies.sql:

-- ============ policies.sql ============
alter table products         enable row level security;
alter table skus             enable row level security;
alter table purchase_batches enable row level security;
alter table purchase_lines   enable row level security;
alter table sales            enable row level security;

-- Any authenticated user of this business may read + write.
-- (Repeat this block for each table.)
create policy "auth read"  on products for select
  using (auth.role() = 'authenticated');
create policy "auth write" on products for all
  using (auth.role() = 'authenticated')
  with check (auth.role() = 'authenticated');

Later, for staff roles: add a role column to a profiles table and change the write policy to using (auth.jwt() ->> 'role' = 'admin').

9 · Testing & accuracy checklist

Do all of this on lyzoo-dev before switching to prod.

Check How to confirm it's accurate
Single batch landed costEnter one PO you already know. Compare the app's Landed £ to your spreadsheet figure — they must match to the penny.
Weight allocationTwo SKUs, different weights, same batch: the heavier one must carry proportionally more shipping+tax. Ratio of add-per-unit = ratio of weights.
Currency conversionA USD batch at rate 0.79: unit £ = unit $ × 0.79. A UK/GBP batch (rate 1) is unchanged.
Weighted average across batchesSame SKU in two batches at different costs. Confirm avg = Σ(landed×qty) ÷ Σqty by hand.
COGS after a saleRecord N units sold; COGS should increase by N × avg cost, and remaining + on-hand value should drop accordingly.
DB vs UI agreeRun select * from inventory_cogs; in the SQL Editor and compare to the Inventory screen — identical numbers.
Upload validationTry a bad sheet (3 columns, blank weight, duplicate SKU). App must reject with a clear message; DB unique constraint blocks dupes.
SecurityLog out and hit a table via the anon key — RLS must return zero rows / deny writes.

10 · Editing & deleting records

The app lets users fix mistakes anywhere: edit a product or its SKUs, edit or delete a purchase batch, or delete a dead product/SKU. Because all cost/COGS numbers live in the SQL views, every edit or delete recalculates inventory & weighted-average COGS automatically — no extra write logic.

Add these cascade rules so deleting a SKU also clears its purchase lines & sales (matching the app's cleanup):

-- make SKU deletes clean up dependent rows
alter table purchase_lines
  drop constraint purchase_lines_sku_id_fkey,
  add  constraint purchase_lines_sku_id_fkey
       foreign key (sku_id) references skus(id) on delete cascade;
alter table sales
  drop constraint sales_sku_id_fkey,
  add  constraint sales_sku_id_fkey
       foreign key (sku_id) references skus(id) on delete cascade;
// --- edit a product (name) ---
await db.from('products').update({ name }).eq('id', productId);

// --- edit a SKU (code / weight) ---
await db.from('skus').update({ sku_code, weight_g }).eq('id', skuId);

// --- delete a SKU (purchase_lines & sales cascade) ---
await db.from('skus').delete().eq('id', skuId);

// --- delete a product (its skus cascade; then its batches) ---
await db.from('purchase_batches').delete().eq('product_id', productId);
await db.from('products').delete().eq('id', productId);

// --- edit a purchase batch: update header, replace its lines ---
await db.from('purchase_batches').update({
  supplier, origin, currency, conversion_rate, shipping_gbp, tax_gbp
}).eq('id', batchId);
await db.from('purchase_lines').delete().eq('batch_id', batchId);
await db.from('purchase_lines').insert(newLines);

// --- delete a batch (lines cascade via schema) ---
await db.from('purchase_batches').delete().eq('id', batchId);

Gate destructive actions behind a confirm dialog in the UI (the prototype does). RLS still applies — only an authenticated session can update/delete.

11 · Dashboard analytics views

The dashboard's Fast-movers, Slow-moving/dead stock, and Low-stock cards all read from one extended view built on inventory_cogs. Months of cover assumes sales accumulate over a 3-month window (monthly velocity = sold ÷ 3); adjust the divisor to your reporting period.

-- SKU metrics: sell-through, monthly velocity, months of cover
create or replace view sku_metrics as
select ic.*,
       case when ic.received > 0
            then ic.sold::numeric / ic.received else 0 end        as sell_through,
       (ic.sold::numeric / 3.0)                                   as per_month,
       case when ic.sold > 0
            then ic.remaining / (ic.sold::numeric / 3.0)
            else null end                                         as months_cover
from inventory_cogs ic;

-- 'Dead' = sold = 0 with remaining > 0
-- select *, (sold = 0) as is_dead from sku_metrics
--   where remaining > 0 order by sell_through asc, on_hand_value_gbp desc;

-- Low stock: below a threshold (parameterise in the query / RPC)
-- select * from sku_metrics where remaining > 0 and remaining < 120
--   order by remaining asc;

The low-stock threshold, default $→£ rate, and reporting currency symbol are app-level Tweaks (props) in the prototype — store them in a small settings table (or app config) if you want them editable in production.

Going to production

Once every check passes in dev: run schema.sql, views.sql, and policies.sql on lyzoo-prod, swap the URL + anon key in supabase.js, push to GitHub, and add the Pages URL to Supabase Auth. Keep dev around for future changes — test there first, always.
